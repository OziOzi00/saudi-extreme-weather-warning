# 三人分工与协作流程

本文件是三人职责、交接顺序和待办的唯一详细清单。技术路线见[统一技术路线](统一技术路线_v1.md)，字段定义见[数据交接契约](数据交接契约.md)。本文件不改变已有代码、NetCDF 字段或风险 JSON Schema。

2026-07-15 由 A 协助推进的 B/C 开发成果及剩余依赖，见[当天进展记录](2026-07-15_B与C协助开发进展.md)。分工归属不因协助实现而改变。

## 总原则

```text
成员 A：GraphCast → MAZU-like NetCDF
成员 B：MAZU-like NetCDF → 风险 JSON + 天气层验证结果
成员 C：风险 JSON → 图谱 → 预警报告 + 灾害影响层验证
```

知识图谱不是成员 C 凭空生产全部内容：A 提供预报、指标、时间和来源事实；B 提供风险、规则、证据和天气验证事实；C 提供区域背景、历史灾害真值、图谱整合、查询和报告。

## 成员 B：MAZU 2025 分析、风险规则与天气验证

**当前状态：开发骨架与草案试跑已由 A 协助完成，仍待 B/全队评审与验证。** 已完成字段审计、ADM1 描述统计、跨源时间语义分级、候选阈值、草案风险引擎和 78 份证据链试跑；两个规则 YAML 仍为 `draft`。冻结规则、正式 Risk JSON 和天气观测验证尚未完成。

### 输入

- 老师提供的 MAZU 2025 指标；A 的 `handoff/mazu_like/*.nc`；A 的变量和时间说明。
- IMERG 实际降水、GHCN（或等价公开站点）温度/降水资料。
- 当前仓库已发布的 ADM1 边界和统一 `region_id`；后续由 C 复核和维护。

### 具体任务

1. **已有 A 协助草案：**复核覆盖率和 ADM1 描述统计，统一 MAZU 与 GraphCast 的日均/日极值/代表时次语义；B 仍需结合典型过程、缺测和观测验证复核 P90/P95 解释。
2. **已有 A 协助候选版：**强降水和高温/热浪 YAML 已写明指标、阈值、评分、区域/季节和缺测处理；B 与全队评审后才能冻结 v1。
3. **已有 A 协助实现：**草案引擎已读取区域摘要并输出逐区域/灾种/lead JSON；B 应复核实现，并在规则冻结后从正式 NetCDF 重算、输出正式 Risk JSON。
4. **已有 A 协助框架：**IMERG/GHCN 标准化、区域/站点匹配、降水与温度指标代码和合成测试已实现；B 仍需取得真实观测，并完成降水误差、命中/漏报/空报、CSI/空间偏差，以及温度 MAE/RMSE、高温日和热浪时序验证。
5. 在风险结果中记录支持、矛盾和缺失证据；天气观测不足时明确标注，不得伪造验证结论。

### 正式输出与边界

## 成员 C：个例真值、知识图谱与 Agent

**当前状态：独立开发工作已由 A 协助推进，仍待 C/全队复核与正式输入。** 仓库已有阿拉伯语区域名和总部映射、候选 case、灾害真值 Schema 与首批证据、Neo4j 开发 bundle/导入器/固定查询，以及受控报告模板。案例尚未批准，对照日尚未通过 B 的观测筛选，真值仍为 `pending`，Neo4j 服务未声明部署，正式报告仍依赖 B 的冻结 Risk JSON。

### 输入

- A 的 NetCDF 元数据与预报事实；B 的 Risk JSON 和后续天气层验证摘要。
- 沙特 ADM0/ADM1、城市和环境背景资料。
- 官方灾害资料、可靠新闻及其他可追溯来源。

### 具体任务

1. 整理 case 清单：包含灾害过程和普通天气对照、起报时间、目标区域、选择依据和灾害资料初步状态；经全队确认后交给 A 批处理。
2. 复核现有 `SA-xx` ADM1 标识，补充可靠的阿拉伯语名称、ADM0/城市对应关系，并评估是否有可替换的官方开放边界。
3. 建立灾害影响真值表，至少记录事件时间、区域、灾种、影响描述、来源和可信度；`yes` 为有可靠影响证据，`no` 为有可靠无明显影响证据，`unknown` 为资料不足，不能把“没找到新闻”写成 `no`。
4. 按[知识图谱设计](知识图谱设计.md)实现 Neo4j Schema、导入和固定查询，整合 A 的预报事实、B 的风险/证据和 C 的背景/灾害资料；图谱只存摘要和关系，不存完整气象栅格。
5. 用受控查询为 Agent 提供输入并生成报告；报告忠实转述风险 JSON、证据、区域背景和验证状态，不得改写 B 的分数、阈值或结论。

### 已有开发输出与边界

- `configs/case_catalog_candidates.csv`：两个事件、两个待筛选对照和一个 demo；全部保留明确状态。
- `handoff/disaster_truth/`：来源目录和逐证据影响真值；目前记录为 `pending`。
- `schemas/candidate_case.schema.json`、`schemas/disaster_impact_record.schema.json`：C 侧稳定字段。
- `handoff/knowledge_graph/`、`neo4j/`：开发 bundle、约束和固定查询。
- `handoff/reports/`：由固定模板生成的接口示例报告。
- `scripts/run_c_development.ps1`：校验→bundle→报告→测试的一键开发复验。

原始灾害材料和 Neo4j 数据库不提交 Git。正式模式还应强制只消费 `rule_status=frozen`；当前示例模式保留醒目免责声明。

### 仍需 C/全队完成

1. 复核首批来源，尽量为灾害影响增加官方原文或第二独立来源，再把 `review_status` 从 `pending` 改为 `reviewed`。
2. 由 B 用 IMERG/GHCN 筛选两个候选对照日；全队确认 event/control、起报时间和测试集划分。
3. 评估能否取得许可清晰、时间更近的官方开放边界；未取得前继续使用并如实标注 2017 参考边界。
4. 本地安装/连接 Neo4j Community 后实机执行约束、导入和固定查询。
5. 接收 B 的冻结 Risk JSON 后生成正式 bundle 与报告，并补充影响层验证结果。

不得重新读取 GraphCast、计算 IVT/PWAT 等指标、制定气象风险阈值、修改 B 的风险分数，或用图谱替代数值风险引擎。

## 正式交接顺序

```text
C 整理候选 case 清单
  → 全队确认 case、起报时间和对照日
  → A 批量生成 MAZU-like NetCDF 与 manifest
  → B 运行冻结规则并完成天气层验证
  → B 输出 Risk JSON
  → C 导入图谱、补充灾害影响真值、生成报告
  → 全队复盘命中、漏报、空报及原因
```

开发可并行：B 可使用现有演示 NetCDF 开发规则读取和 JSON 接口；C 的 Schema 示例、图谱导入与报告模板已经完成开发复验，无需等待所有历史 case 完成。

4. 全链路联调：GraphCast → MAZU-like → Risk JSON → 图谱/报告 → 天气层与影响层验证。
